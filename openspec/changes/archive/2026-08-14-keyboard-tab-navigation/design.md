## Context

現在のタブ切り替えは `App` の `window` キーダウン（バブル）ハンドラで `Cmd+1`〜`9` と `Cmd+N` だけを処理している。xterm はヘルパー textarea 上の keydown で入力を受け取り `onData` で PTY へ送るため、バブル段階の `window` リスナが受け取る時点では既にターミナルへ届いている。`Ctrl+J`（^J = LF）のように「本来ターミナルに意味があるキー」をプレフィックスとして横取りするには、xterm より先にイベントを止める必要がある。

コピー / ペーストは `clipboard.ts` の純粋関数（`clipboardShortcutAction` / `applyClipboardShortcut`）を xterm の `attachCustomKeyEventHandler` から呼ぶ形で実装済み。フォーカス制御は `terminal-focus.ts` の純粋関数、入力可否は `terminal-input.ts` に切り出されており、「判断は純粋関数、副作用は React 側」という分担が既にある。設定の永続化は `PATCH /api/config` 即時保存とサーバ側 `validate` によるロールバック（起動シェルのパス編集）が前例となる。

プレフィックス方式は「待機状態」という 1 つのモード状態を持つ。この状態はターミナルにフォーカスがあるときも、サイドバーにフォーカスがあるときも同じように扱いたいので、状態の置き場所を 1 か所に決めることがこの設計の中心になる。

## Goals / Non-Goals

**Goals:**

- プレフィックス → 次 / 前キーの 2 ストロークで、サイドバー順の隣のタブへ移動できる（端はラップ）
- 有効時、プレフィックスと移動キーが PTY に届かない
- 割り当て（プレフィックス / 次 / 前）と有効・無効を設定モーダルから変更でき、`config.json` に永続化される
- 待機中であることが画面から分かり、`Escape` / タイムアウト / ウィンドウのフォーカス喪失で解除される
- 既存ショートカット（`Cmd+1..9`、`Cmd+N`、`Cmd+C`、`Cmd+V`）と IME 入力を壊さない

**Non-Goals:**

- 全操作を対象にした汎用キーマップエディタ（新規タブ・閉じる・分割などの再割り当て）
- プレフィックスなしの単発ショートカットによるタブ移動
- プレフィックスの多段化（`Ctrl+J` `Ctrl+J` のような二重押しや複数プレフィックス）
- キー割り当てのインポート / エクスポート、プリセット（tmux 風 / screen 風）
- 非 Latin キーボードレイアウトでの物理キー位置ベースのマッチング（`KeyboardEvent.code` 基準）

## Decisions

### 1. キーの横取りは `window` の capture フェーズで行う

- **選択**: `App` に `keydown` の capture リスナ（`{ capture: true }`）を 1 つ足し、そこでプレフィックスと移動キーを判定する。該当したら `preventDefault()` と `stopPropagation()` を呼び、xterm の textarea までイベントを届けない
- **理由**: capture は window → … → textarea の順に走るため、xterm がキーを読む前に止められる。ターミナルにフォーカスがある場合と、サイドバーなど他要素にフォーカスがある場合を 1 つの経路で扱える
- **代替案**: xterm の `attachCustomKeyEventHandler`（コピー / ペーストと同じ経路）→ ターミナルにフォーカスがあるときしか発火せず、待機状態を `App` と共有する必要が出るため不採用
- **代替案**: バブルフェーズの既存ハンドラを流用 → xterm が先に ^J を PTY へ送ってしまうため不採用
- 既存の `Cmd+1..9` / `Cmd+N` ハンドラはバブルのまま変更しない（`Cmd` 系は xterm が PTY へ送らないため実害がない）

### 2. 判定ロジックは純粋モジュール `web/src/keymap.ts` に切り出す

- **選択**: 次を純粋関数として実装し、React 側は結果に従って `select()` や `setState` を呼ぶだけにする
  - `normalizeKeyEvent(e)`: `KeyboardEvent` を `ctrl+shift+j` 形式へ正規化。修飾キー単独（`Control` など）や IME 変換中（`isComposing` / `keyCode === 229`）は `null`
  - `formatBinding(spec)`: 表示用（`ctrl+j` → `Ctrl+J`）
  - `validateBindings(bindings)`: プレフィックスの修飾キー必須、次 / 前の重複、`escape`、既存ショートカット（`meta+1`..`meta+9`、`meta+n`、`meta+c`、`meta+v`）との衝突を検査
  - `resolveChordKey(pending, spec, bindings)`: `{ pending, action }` を返す。`action` は `none` / `arm` / `next` / `prev` / `cancel`
  - `neighbourTabIndex(count, activeIndex, direction)`: ラップ込みの移動先計算
- **理由**: 既存の `terminal-focus.ts` / `terminal-input.ts` / `clipboard.ts` と同じ分担。DOM なしで `node --test` から直接テストでき、状態遷移を網羅的に検証できる
- **代替案**: `App` 内に直接ロジックを書く → 分岐（待機中 / 無効 / テキストフィールド / IME / ラップ）が多く、テストがフルレンダリング前提になるため不採用

### 3. 待機状態は `App` の state + タイマー ref で持つ

- **選択**: `pendingPrefix`（boolean 相当の state）と `window.setTimeout` の ref を `App` に置く。`arm` でタイマーを張り直し、`cancel` / 移動実行 / `Escape` / `blur` / モーダル open で解除する。タイムアウトは 3 秒
- **理由**: 待機表示（インジケータ）が再レンダリングを必要とするため state が要る。タイマーは再レンダリングに巻き込まないよう ref に置く
- **代替案**: タイムアウトなし（tmux と同じ）→ 押しっぱなしの待機が残り、次のキーが 1 つ食われる事故が起きるため不採用
- **代替案**: タイムアウト時間も設定可能にする → 設定項目が増える割に価値が薄いので固定値

### 4. 抑止条件は既存の判定を再利用する

- **選択**: 設定モーダル / メモ編集が開いているとき（既存の `settingsOpen` / `memoSessionId`）と、テキストフィールドにフォーカスがあるとき（`clipboard.ts` の `isTextFieldElement`）はショートカットを完全に無効化し、`preventDefault` もしない
- **理由**: メモ入力に `n` / `p` が打てなくなる事故を防ぐ。既存の判定関数をそのまま使えば挙動がぶれない
- **代替案**: モーダル側で個別に `stopPropagation` する → 抑止条件が散らばるため不採用

### 5. 既定は無効（`enabled: false`）

- **選択**: 既定値は `enabled: false`、割り当ては `ctrl+j` / `n` / `p` を最初から入れておき、設定でトグルを ON にするだけで使えるようにする
- **理由**: `Ctrl+J` は vim の挿入モードや fzf などターミナル内で実際に使われる。既存ユーザーの ^J を黙って奪わない。有効化は設定モーダルで 1 クリック
- **代替案**: 既定で有効 → 追加した本人以外（および将来の自分）にとって、ターミナル内アプリのキーが理由不明で効かなくなるため不採用。既定を有効にしたい場合は `Defaults()` の 1 行変更で切り替えられる

### 6. 設定値は `config.json` の `key_bindings` オブジェクトに置く

- **選択**: 次の形で保存する。フロントの `AppConfig` にも同じ形を追加する

  ```json
  "key_bindings": {
    "enabled": false,
    "prefix": "ctrl+j",
    "next_tab": "n",
    "prev_tab": "p"
  }
  ```

- **理由**: 将来ショートカットが増えてもキーを足すだけで済む。既存の `notification` と同じネスト構造なので、`PATCH /api/config` の部分適用（`json.Unmarshal` の上書き）も同じ挙動になる
- **代替案**: トップレベルに `tab_nav_prefix` などを並べる → 設定が増えるほど散らかるため不採用
- 旧 `config.json`（キーなし）は `applyDefaults` で空文字の項目を既定値で埋める。`enabled` はゼロ値がそのまま既定（false）になる

### 7. 検証はサーバを正とし、フロントでも同じ規則で先に弾く

- **選択**: Go の `validate` に割り当て検査を追加し、不正な `PATCH` は 400 で拒否する。フロント側も `validateBindings` で送信前に検査し、日本語のエラーを即時表示する。保存失敗時は最後に永続化された値へ戻す（起動シェルのパス編集と同じロールバック）
- **理由**: 設定ファイルを直接編集された場合もサーバが弾ける。UI 側の即時検証は往復なしでエラー理由を出せる
- **代替案**: サーバ検証のみ → エラーが往復後になり、記録 UI の体験が落ちる
- **トレードオフ**: 規則が 2 実装に分かれる。規則は 4 つ（修飾キー必須 / 重複 / `escape` / 予約ショートカット）に限定し、双方のテストで同じケースを並べる

### 8. 割り当ての入力は「キー記録」方式にする

- **選択**: ボタンを押すと記録モードに入り、次の 1 打鍵を捕捉して割り当てる。記録中は capture リスナで打鍵を消費し、他のショートカットとモーダルの `Escape` クローズより先に処理する。`Escape` は記録のキャンセル
- **理由**: `ctrl+j` のようなテキスト入力は打ち間違いと表記ゆれ（`Control+J` / `C-j`）を生む。記録なら正規化済みの値だけが入る
- **代替案**: テキスト入力 + パーサ → 表記ゆれの吸収と検証が増えるため不採用
- 記録中は `stopPropagation()` により `SettingsModal` の `window` バブル `Escape` ハンドラへ届かないようにする（capture で止めれば同一ノードのバブル訪問は起きない）

### 9. 待機インジケータは既存 UI に足す最小要素にする

- **選択**: 待機中だけ表示される小さなピル（例: `Ctrl+J …`）を `App` が描画し、`index.css` にスタイルを足す。新しい依存は入れない
- **理由**: プレフィックスが armed であることが見えないと、次の 1 打鍵が消えた理由が分からない
- **代替案**: トースト（`toast-error` の流用）→ エラー表示と混同するため不採用

## Risks / Trade-offs

- [有効化するとターミナル内アプリの `Ctrl+J` が使えなくなる] → 既定は無効。設定で任意のプレフィックスへ変更でき、無効化も 1 クリック
- [capture リスナが IME や通常入力を壊す] → `isComposing` / `keyCode === 229` と修飾キー単独を `null` 扱いにし、`preventDefault` はプレフィックスと移動キーが一致したときだけ呼ぶ
- [待機状態が残り、次の 1 打鍵が食われる] → 3 秒タイムアウト、`Escape`、ウィンドウ `blur`、モーダル open で解除。待機中はインジケータで可視化
- [フロントと Go で検証規則がずれる] → 規則を 4 つに限定し、両方のテストで同じケース（修飾キーなし / 重複 / `escape` / `Cmd+N` 衝突）を検証する
- [非 Latin レイアウトや Dead キーで意図した割り当てにならない] → `KeyboardEvent.key` の小文字を基準にする。物理キー位置（`code`）ベースは Non-Goals とし、記録 UI で実際に押したキーがそのまま入ることで実害を抑える
- [`Cmd+1..9` との併存] → プレフィックスに `Cmd+1..9` / `Cmd+N` / `Cmd+C` / `Cmd+V` を割り当てられないよう検証で弾く
- [タブ移動時にアタッチ処理が走る] → 既存の `select()` を経由するため、フォーカス・未読解除・WS アタッチは既存経路と同じ

## Migration Plan

1. Go の `key_bindings` 追加（既定値 + `applyDefaults` + `validate`）→ 旧 `config.json` はそのまま読める（追加のみ、破壊的変更なし）
2. フロントの `keymap.ts` とキー処理 → 既定無効なので、この時点でも既存の挙動は変わらない
3. 設定モーダルの「キーボード」カテゴリ → ここで初めてユーザーが有効化できる
4. ロールバック: 設定で `enabled: false`（またはコード側で capture リスナを外す）。`config.json` に残る `key_bindings` は無視されるだけで害はない
