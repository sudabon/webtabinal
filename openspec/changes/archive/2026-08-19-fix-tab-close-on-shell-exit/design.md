## Context

動機は proposal.md の Why を参照。要求は specs/ 配下のデルタを参照。

現状の実装上の制約として押さえておくべき点:

- `internal/session/session.go` は PTY ごとに `readLoop`（出力読み出し・OSC パース）と `waitLoop`（`cmd.Wait()`）の 2 goroutine を回す。`waitLoop` は `Wait()` が返った直後に `State=exited` を設定し `onExit` を呼ぶ。`readLoop` の完了は待っていない。
- `internal/session/manager.go` の `handleExit` が `cfg.CloseTabOnCleanExit && *info.ExitCode == 0` でタブ削除を判定している唯一の場所。
- OSC 9973 は既に WebTabinal 専用の私的シーケンスで、現在は `9973;cmd;<base64>` のみを解釈し、それ以外のサブタイプはイベントを生成せず無視される。
- zsh 統合は ZDOTDIR 注入、bash 統合は `--rcfile` 注入で読み込まれ、どちらも `WEBTABINAL_SESSION_ID` が無ければ何もしない。bash 側は既存の `PROMPT_COMMAND` / `DEBUG` トラップを退避して連鎖させる実装パターンを既に持っている。
- 非統合シェル（fish / sh など）は `Integrated=false` のままで、フォールバック検出も `starting` 状態のセッションには何もしないため、OSC 由来の手掛かりが一切得られない。

実機で確認した事実（本設計の前提）:

- bash / zsh とも、引数なしの `exit` と Ctrl+D は直前のコマンドの終了ステータスを返す。`false` の直後に終了すると exit=1 になる。
- bash の `EXIT` トラップ、zsh の `zshexit` フックはいずれも `exit` / Ctrl+D の両方で発火し、そこから書いた OSC は PTY マスタ側に届く。ただし到達するのは**プロセス終了直前の最後のバイト列**である。

## Goals / Non-Goals

**Goals:**

- ユーザーが自分で終了させたシェルのタブは、終了ステータスに関わらず閉じる。
- 落ちた／起動に失敗したシェルのタブは残し、出力を読めるようにする。
- 統合が効いていないシェルの挙動は今日と同じに保つ。
- 設定ファイルの移行を発生させない。

**Non-Goals:**

- 設定 UI に新しいトグルを足さない（`close_tab_on_clean_exit` は現状 `config.json` のみで扱う）。
- 「非 0 終了でも閉じる／閉じない」をユーザーが細かく選べるようにはしない。判定はシェルの終了経路で決める。
- 非統合シェルに対して終了経路を推定する仕組み（プロセス監査など）は導入しない。
- 終了したタブの UI（restart / close の見せ方）は変更しない。

## Decisions

### 1. 終了シグナルは OSC 9973 のサブタイプとして送る

`9973;exit;<code>` を新設し、パーサに `EventShellExit` を追加する。

- **なぜ**: 9973 は既に WebTabinal 専用で、他アプリと衝突しない。パーサの分岐が 1 箇所増えるだけで、未知のサブタイプが無視される既存の性質もそのまま活かせる。
- **代替案**: OSC 133;D を終了時にも流す → コマンド終了と区別できず、`ExitCode` と状態機械を汚す。別の OSC 番号を新設 → 私的番号を 2 つ管理することになり利点がない。
- `<code>` はデバッグと将来の表示のために載せるが、閉じる判定には使わない（シグナルの有無だけで判断する）。

### 2. 発行はシェルの終了フックに載せ、ユーザーのフックを壊さない

- zsh: `add-zsh-hook zshexit __webtabinal_zshexit`。`add-zsh-hook` は既に precmd / preexec / chpwd で使っており、`zshexit` も同じ仕組みでユーザーのフックと共存する。
- bash: `trap` の EXIT に載せる。既存の DEBUG トラップと同じ要領で `trap -p EXIT` の内容を退避し、WebTabinal のハンドラから元のコマンドを `eval` して連鎖させる。
- 冪等性: 既存の `WEBTABINAL_INTEGRATION_LOADED` ガードで二重ロードを防いでいるため、フック登録も 1 回きり。ハンドラ側にも「一度送ったら送らない」フラグを置き、シグナルは 1 セッション 1 回に限定する。
- **なぜフック方式か**: シェル自身が終了経路を知っている唯一の主体だから。デーモン側から `exit` の入力文字列を検出する方式は、`logout`・スクリプト経由の終了・ヒアドキュメント中の `exit` などを取りこぼす／誤検知する。

### 3. `waitLoop` は `readLoop` の完了を上限付きで待ってから `onExit` を呼ぶ

終了シグナルは最後のバイト列として届くため、`cmd.Wait()` が返った瞬間には未処理の可能性が高い。`readLoop` の終了を知らせるチャネルを追加し、`waitLoop` は `Wait()` の直後にそれを待ってから `State=exited` の確定と `onExit` を行う。待ち時間には上限（数百 ms 程度）を設け、スレーブ fd を掴んだ子プロセスが残っていて `readLoop` が終わらない場合でも先に進む。

- `done` チャネル（`Close()` が SIGHUP 後の待ち合わせに使う）のクローズ時点は変えない。遅らせるのは状態確定と `onExit` のみで、`Close()` の応答性に影響させない。
- `applyEvent` は `State==exited` で早期 return するため、ドレインを状態確定より前に置く順序が必要。
- **代替案**: `readLoop` 側から終了を駆動する → `Wait()` が返らないケース（PTY だけ閉じた）で終了を取りこぼす。固定 sleep → 遅い環境で取りこぼし、速い環境で無駄な待ちになる。

### 4. 閉じる判定は次の順序で評価する

`handleExit` の判定を以下に置き換える。上から順に最初に一致したものを採用する。

1. `close_tab_on_clean_exit` が false → 残す
2. 統合済み（`Integrated=true`）かつ初回プロンプトを一度も観測していない → 残す
3. 終了シグナルを受け取っている → 閉じる
4. 終了コードが 0 → 閉じる
5. それ以外 → 残す

- ルール 2 の「初回プロンプト」は OSC 133;A の観測（`EventPrompt`）で判定し、セッションに `promptSeen` フラグとして持つ。統合スクリプトは読み込み直後に OSC 7 を出すため `Integrated` だけでは「rc の途中で `exit` した」ケースを弾けない。プロンプトまで到達したかどうかが「対話できる状態になった」の実質的な指標になる。
- ルール 2 を `Integrated=true` に限定するのは、非統合シェルでは `promptSeen` が永久に false のままで、無条件に全タブが残ってしまうため。非統合シェルはルール 4 に落ち、今日と同じ挙動になる。
- **代替案**: 「シグナルが無ければ終了コード 0」ではなく「シグナルが無ければ常に残す」 → 非統合シェルで exit 0 でもタブが残るようになり、既存ユーザーの挙動が壊れる。

### 5. 設定キーは変えない

`close_tab_on_clean_exit` の名前・型・既定値 `true` を維持し、意味だけを広げる。名前と意味のずれは README の説明で吸収する。

- **なぜ**: キーを増やす／改名すると、既存 `config.json` の移行と後方互換の埋め込みロジックが必要になり、得られるものに対して割に合わない。挙動を「ユーザーが閉じたら閉じる」に寄せるのが本来の意図であり、新しい選択肢を提供する変更ではない。

## Risks / Trade-offs

- **統合スクリプトのバージョンが上がり、Application Support 配下のファイルが上書きされる** → 既存の書き出し・上書きの仕組みをそのまま使う。ユーザーがスクリプトを手で編集している想定は元々ない。
- **ユーザーの `EXIT` トラップとの競合で、ユーザー側のトラップが失われる** → DEBUG トラップで実績のある「退避して `eval` で連鎖」パターンを踏襲し、連鎖が効くことをテストで固定する。
- **`readLoop` のドレイン待ちでタブ削除が数百 ms 遅れる** → 上限を短く取る。ユーザーには「exit を打ってからタブが消えるまで」の遅延として見えるが、体感できる差にはならない範囲に収める。
- **スレーブ fd を握った子プロセス（バックグラウンドジョブ）が残ると `readLoop` が終わらない** → 上限タイムアウトで先に進む。その場合はシグナルを取りこぼし、ルール 4（終了コード 0）にフォールバックする。最悪でも今日と同じ挙動。
- **これまで残っていたタブが閉じるようになる** → 挙動変化として README に明記する。スクロールバックを残したいユーザーは `close_tab_on_clean_exit` を false にできる。
- **rc の途中で `exit` するようなシェル設定** → ルール 2 のプロンプト未到達ガードで残す。ただし rc が正常に完走してプロンプトを出したあと、ユーザーのフックが `exit` を呼ぶような構成ではタブが閉じる。これは「シェルが自分の意思で終了した」の定義どおりで、許容する。

## Migration Plan

1. 統合スクリプトのバージョン文字列を上げる。デーモン起動時に Application Support 配下のファイルが上書きされる。
2. 既に起動中のセッションは古い統合スクリプトのままなので終了シグナルを出さない。その場合はルール 4 に落ち、今日と同じ挙動になる。新しいタブから順に新しい挙動になる。
3. ロールバックはコード revert のみ。永続データのスキーマ変更が無いため、`config.json` にも Application Support のレイアウトにも後戻り手順は要らない。
